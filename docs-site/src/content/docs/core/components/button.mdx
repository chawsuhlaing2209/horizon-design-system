### When to use it

- Buttons communicate actions that people can take. They are typically placed throughout the UI, in places like: Dialogs, Modal windows, Forms, Cards, Toolbars<br />They can also be placed within standard button groups.
- Use visually-prominent filled buttons for the most important actions
- Use buttons for discrete actions.
- A button container’s width is dynamically set to fit its label text
- Button container width can be responsive, which allows it to stretch horizontally

**Where it goes.** In a form's action row, below an email input: a filled `type="submit"` Button with an outlined "Cancel" Button beside it ([InForm](https://horizon-design-system-delta.vercel.app/?path=/story/components-button--in-form)). In the slot of a vertical Card, as an outlined "View details" Button ([InCard](https://horizon-design-system-delta.vercel.app/?path=/story/components-button--in-card)).

<Aside type="caution" title="When not to use it">

- Don’t clutter your UI with too many buttons. Consider presenting low-priority actions in overflow menus or as icon buttons. **Instead:** overflow menus or as icon buttons.
- A button container’s width shouldn’t be narrower than its label text
- Don’t wrap text. For maximum legibility, label text should remain on a single line.

</Aside>

### Best practice

- Use sentence case for button label text, capitalizing the first word and proper nouns
- Buttons can move in the layout, but elements should remain in the same order

### What each variant is for

| Property | Value | What it is for |
|---|---|---|
| `variant` | `filled` | `filled` is the high-emphasis button, for the most important action in a view. |
| `variant` | `outlined` | `outlined` is the medium-emphasis button, for a secondary action beside a filled one. |
| `state` | `enable` | `enable` is the resting button, ready for input. |
| `state` | `hover` | `hover` is the button under a pointer. |
| `state` | `focused` | `focused` is the button holding keyboard focus. |
| `state` | `disabled` | `disabled` also sets the native `disabled` attribute. |

### Import

```tsx
import { Button, type ButtonProps, type ButtonVariant, type ButtonState } from '@theproductiveschedule/horizon-design-system';
import '@theproductiveschedule/horizon-design-system/tokens.css';
import '@theproductiveschedule/horizon-design-system/styles.css';
```

The stylesheets are imported once, at the root of the app. `src/index.ts` decides what is public; anything not exported there is internal.

### Props

| Prop | Type | Default | What it does |
|---|---|---|---|
| `variant` | `ButtonVariant` | `filled` | Figma `variant`.<br/>`filled` is the high-emphasis button, for the most important action in a view.<br/>`outlined` is the medium-emphasis button, for a secondary action beside a filled one. |
| `state` | `ButtonState` | `enable` | Figma `state`.<br/>`enable` is the resting button, ready for input.<br/>`hover` is the button under a pointer.<br/>`focused` is the button holding keyboard focus.<br/>`disabled` also sets the native `disabled` attribute. |
| `children` | `ReactNode` | **required** | The label. Compose an icon alongside it and the gap token applies. |
| `className` | `string` | — | Merged after `hds-button`, never in place of it. Not a Figma property. |

`ButtonProps` also accepts `Omit<ButtonHTMLAttributes<HTMLButtonElement>, 'disabled' | 'children'>`.

Prop names mirror the Figma property names exactly. That is a rule of the system, recorded in `CLAUDE.md`, so a design change and a code change stay the same conversation.

### The variant matrix

**Button** (`26:70`) — `variant` (`filled` · `outlined`), `state` (`enable` · `hover` · `focused` · `disabled`). Variant × State = **8 variants**.

Every variant in the Figma set has a story. That is the contract between design and code: a variant with no story is a guaranteed QA failure, and a story with no variant behind it is something nobody designed.
